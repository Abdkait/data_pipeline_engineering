# Подготовка к защите архитектуры

## Что мы делаем и зачем

Мы проектируем пайплайн обработки юридических документов для системы типа Консультант Плюс. В такой системе ежедневно появляются новые законы, судебные решения, редакции — и всё это нужно собрать, обработать, проиндексировать и доставить пользователям.

**Почему Kafka, а не просто база данных?**

Потому что у нас поток событий, а не статичные данные:
- Документы приходят непрерывно из разных источников.
- Их нужно обработать в несколько этапов (парсинг → тегирование → индексация → уведомления).
- Разные потребители хотят одни и те же данные (поисковый индекс, уведомления, аналитика).
- Система должна выдерживать нагрузку и не терять данные.

---

## Почему разбили именно на эти 5 топиков?

**Принцип: один топик = один тип данных с одним жизненным циклом.**

Нельзя смешивать законы и клики в одном топике, потому что:
- **законы:** мало данных, хранить 30 дней, терять НЕЛЬЗЯ.
- **клики:** много данных, хранить 7 дней, терять можно.

Разные retention, разные гарантии, разная нагрузка → разные топики.

**Три сырых топика (`laws`, `court-decisions`, `revisions`)** — потому что:
- Разные источники данных (ГД, суды, внутренние редакторы).
- Разные форматы сообщений.
- Разная нагрузка (судебных решений на порядок больше, чем законов).
- Разные команды могут разрабатывать парсеры независимо.

**Один обработанный топик (`processed-documents`)** — потому что:
- Все документы после обработки выглядят одинаково (есть id, title, tags, text).
- Потребителям (поисковику, уведомлениям) неважно, откуда пришёл документ.

**Отдельный топик `user-events`** — потому что:
- Это совсем другой тип данных (кликстрим, а не документы).
- Другие гарантии доставки (можно терять).
- Другие потребители (аналитика).

## Почему именно такое количество партиций

- **laws:** 3 партиции — законов мало (десятки в день).
- **court-decisions:** 6 партиций — решений много (тысячи в день).
- **revisions:** 3 партиции — редакций немного.
- **processed-documents:** 6 партиций — сюда пишут 3 процессора, нужна пропускная способность.
- **user-events:** 3 партиции — для учебного проекта хватает.

**Главное правило:** количество партиций = максимальный параллелизм. Если в топике 6 партиций, можно запустить до 6 consumer'ов в одной группе, и каждый будет читать свою партицию.

---

## Почему именно такие ключи

Ключ определяет, в какую партицию попадёт сообщение: `partition = hash(key) % num_partitions`.

- **laws (`key = document_id`):** все события про один закон в одной партиции → порядок обработки гарантирован.
- **court-decisions (`key = court_id`):** решения одного суда обрабатываются последовательно → равномерное распределение (судов много).
- **revisions (`key = document_id`):** КРИТИЧНО: редакция v2 не обработается раньше v1 → потому что они в одной партиции, а внутри партиции порядок гарантирован.
- **user-events (`key = user_id`):** действия одного юзера по порядку → можно строить сессии.

Почему в court-decisions ключ court_id, а не case_id?
если ключ = `case_id`, то каждое дело в своей партиции — слишком мелкое дробление, неравномерное распределение. `court_id` даёт хорошую группировку: решения одного суда идут последовательно, а между судами — параллельно.

## Про политики хранения

### `delete` (laws, court-decisions, user-events)
Kafka удаляет сообщения старше N дней. Подходит для потоковых данных, которые после обработки сохраняются в другое хранилище (БД, поисковый индекс).

### `compact` (revisions, processed-documents)
Kafka оставляет ТОЛЬКО последнее сообщение для каждого ключа.

Пример для revisions:
- offset 0: key=law-123, rev=1 ← удалится при компакции
- offset 1: key=law-123, rev=2 ← удалится при компакции
- offset 2: key=law-123, rev=3 ← ОСТАНЕТСЯ (последнее)

Зачем: если мы перезапускаем `search_indexer`, ему нужно актуальное состояние каждого документа. С `compact` он прочитает только последнюю версию, не перелопачивая историю.

А зачем compact для revisions, если там порядок важен?
порядок важен при первичной обработке (`revision_processor` читает v1→v2→v3 по порядку и применяет последовательно). Но после обработки старые редакции не нужны в Kafka — полная история хранится в БД. Compact оставляет только последнюю версию для случая, если нужно переобработать.

## Про гарантии доставки

### At least once (`acks=all`) — laws, court-decisions, revisions, processed-documents
Продюсер ждёт подтверждения от ВСЕХ реплик. Сообщение гарантированно не потеряется. Может быть дубль (если ACK потерялся, продюсер повторит отправку).

Почему именно так:
- Потерять закон = пользователь не увидит актуальный НПА.
- Потерять судебное решение = юрист не найдёт нужный прецедент.
- Это НЕДОПУСТИМО для правовой системы. Дубль — не страшно, его можно отфильтровать по `document_id`.

### At most once (`acks=1`) — user-events
Продюсер ждёт подтверждения только от лидера. Быстрее, но при падении лидера сообщение может потеряться.

Почему именно так:
- Потерять один клик пользователя = ничего страшного.
- Аналитика всё равно статистическая.
- Зато не создаём лишнюю нагрузку на критичный путь.

## Зачем две группы на одном топике

`processed-documents` читают ДВЕ группы:
- `cg-search-indexer` → обновляет поисковый индекс
- `cg-notification-sender` → рассылает уведомления подписчикам

Каждая группа получает ВСЕ сообщения независимо. У каждой группы свой offset (свой прогресс чтения).

Почему не одна группа:
Если одна группа — Kafka РАСПРЕДЕЛИТ сообщения между consumer'ами (каждый получит часть). А нам нужно чтобы И индексер, И нотификатор получили КАЖДОЕ сообщение. Это паттерн "публикация-подписка" (pub-sub).

### Пользовательский сценарий Fan-out
Новый закон принят → `law_processor` обработал его → Записал в `processed-documents`.

Нужно ОДНОВРЕМЕННО и НЕЗАВИСИМО:
1. **Search Indexer:** Закон появился в поиске на сайте.
2. **Notification Sender:** Юрист Иванов получил push-уведомление.

Оба действия должны произойти. При этом индексация занимает 100мс, а отправка уведомлений — 2 секунды. Один сервис не должен ждать другой. Если `notification_sender` упал — индексация всё равно работает.

### Независимость при сбоях
Если `notification_sender` упал на 2 часа:
- `cg-search-indexer` работает нормально, индексирует документы. Пользователи находят новые законы.
- `cg-notification-sender` перезапустился через 2 часа, догнал свой offset и отправил все пропущенные уведомления. Данные НЕ потерялись.

### Добавление нового потребителя
Через полгода нужна ML-система для классификации документов.
Мы просто добавляем ТРЕТЬЮ группу (`cg-ml-classifier`). Она начнёт с `earliest` и прочитает всю историю. Существующие сервисы ничего не узнают о новом consumer'е, ноль изменений в их коде.

## Про гарантию порядка редакций

1. Все редакции одного документа имеют ОДИНАКОВЫЙ ключ (`document_id`).
2. Kafka отправляет сообщения с одинаковым ключом в ОДНУ партицию (`partition = hash("law-123") % 3`).
3. Внутри одной партиции порядок ГАРАНТИРОВАН (это append-only лог).

Результат:
Партиция 0: `[law-123 rev1] → [law-123 rev2] → [law-123 rev3]`
Consumer читает строго по порядку. Невозможно получить rev3 раньше rev1.

*ВАЖНО:* порядок гарантирован ТОЛЬКО внутри одной партиции. Между разными партициями порядка нет, но нам это и не важно, так как это разные документы без зависимости друг от друга.

---

## Если consumer упадёт...

1. Consumer периодически коммитит offset (номер последнего обработанного сообщения) в Kafka.
2. Если consumer падает:
   - Kafka замечает это (нет heartbeat).
   - Происходит rebalance: партиции перераспределяются между оставшимися consumer'ами в группе.
   - Новый consumer продолжает с последнего закоммиченного offset.
   - Несколько сообщений могут обработаться повторно (это нормально для at-least-once).
3. Если consumer один в группе и он падает:
   - Никто не читает, сообщения копятся в Kafka.
   - Когда consumer перезапустится — прочитает всё с последнего offset. Данные НЕ теряются.
