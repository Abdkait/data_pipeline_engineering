# Kafka-пайплайн "Консультант Плюс"

Учебный проект, реализующий архитектуру потоковой обработки документов (законы, судебные решения, редакции) и пользовательских событий с использованием Apache Kafka.

Подробное описание архитектуры, топиков, партиций и гарантий доставки находится в файле [ARCHITECTURE.md](ARCHITECTURE.md).

## Быстрый старт

Для запуска проекта и прогона тестов выполните следующие команды в терминале:

```bash
# 1. Поднимаем инфраструктуру (Kafka + ZooKeeper) в Docker
make up

# 2. Создаем и активируем виртуальное окружение Python
python3 -m venv venv
source venv/bin/activate

# 3. Устанавливаем зависимости
pip3 install -r requirements.txt

# 4. Ждем готовности Kafka и создаем топики
make setup

# 5. Запускаем все интеграционные тесты
make test
```

*Чтобы остановить и удалить контейнеры Kafka, используйте команду `make down`.*

## Описание тестов

Проект включает набор интеграционных тестов (написанных на `pytest`), которые проверяют корректность работы архитектуры и консьюмеров. Каждый тест проверяет отдельный сценарий:

### 1. Базовый поток обработки (`test_basic_flow.py`)
**Сценарий A:** Проверяет полный путь документа от продюсера до финального топика.
- Запускает `law_processor` в фоновом потоке.
- Отправляет сырой закон в топик `laws`.
- Ожидает появления обработанного документа в топике `processed-documents`.
- Проверяет, что процессор успешно прочитал сообщение, добавил нужные теги (например, "налоги") и сохранил результат.

### 2. Гарантия порядка (`test_revision_order.py`)
**Сценарий B:** Проверяет, что сообщения с одинаковым ключом обрабатываются строго последовательно.
- Отправляет 3 разные редакции одного документа (одинаковый `document_id`) в топик `revisions`.
- Читает их консьюмером и проверяет, что порядок получения (1, 2, 3) строго совпадает с порядком отправки, так как они попали в одну партицию.

### 3. Паттерн Fan-out (`test_fanout.py`)
**Сценарий C:** Проверяет независимое чтение одного топика разными сервисами.
- Отправляет обработанный документ в `processed-documents`.
- Создает двух консьюмеров с разными `group.id` (имитация `search_indexer` и `notification_sender`).
- Убеждается, что *оба* сервиса получили одно и то же сообщение независимо друг от друга.

### 4. Параллелизм и партиционирование (`test_parallel.py`)
**Сценарий D:** Проверяет правильное распределение нагрузки.
- Отправляет 100 судебных решений с 5 разными ключами (`court_id`) в топик `court-decisions` (в котором 6 партиций).
- Читает все сообщения и проверяет два условия:
  1. Все решения по одному суду (одинаковый ключ) всегда попадают в одну и ту же партицию.
  2. Задействовано более одной партиции (данные реально распределяются по кластеру, обеспечивая параллелизм).

### 5. Пользовательская аналитика (`test_user_analytics.py`)
**Сценарий E:** Проверяет бизнес-логику консьюмера аналитики.
- Отправляет набор различных событий (просмотры и поисковые запросы) от разных пользователей в топик `user-events`.
- Ждет получения всех событий.
- Проверяет, что аналитика корректно подсчитала количество просмотров для каждого документа, игнорируя при этом события других типов (например, `search`).
