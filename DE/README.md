# ConsultantPlus Session Analytics (Spark / Scala)

Учебная Spark-задача: вычисление двух показателей по логам пользовательских сессий системы
КонсультантПлюс.

## Задача

1. **Метрика 1** — количество раз, когда в карточке поиска производили поиск документа с
   идентификатором `ACC_45616` (т.е. он использовался как значение параметра карточки).
2. **Метрика 2** — количество открытий каждого документа, найденного через быстрый поиск (QS),
   за каждый день.

## Результаты

| Показатель | Значение |
|---|---|
| Обработано сессий | 10 000 |
| Битых/пропущенных строк | 0 |
| **Метрика 1** (поисков `ACC_45616` в карточке) | **24** |
| **Метрика 2** — уникальных пар (день, документ) | 75 516 |
| **Метрика 2** — суммарно открытий | 87 934 |

Результаты выполнения лежат в `output/`:
- `output/card_searches_for_target/part-00000` — метрика 1;
- `output/quick_search_doc_opens_by_day/part-*.csv` — метрика 2 (`day, document_id, open_count`).

Корректность чисел подтверждена независимой эталонной реализацией (полное совпадение по всем
строкам метрики 2 и по метрике 1).

## Формат данных

Каждый файл в `Data/` — одна сессия. Кодировка **CP1251**, файлы без финального перевода строки.
Идентификаторы документов и `searchId`, а также метки времени — ASCII, поэтому токенизация по
пробелам устойчива независимо от кодировки.

```
SESSION_START dd.MM.yyyy_HH:mm:ss
QS dd.MM.yyyy_HH:mm:ss {текст запроса}
<searchId> <docId> <docId> ...                  # результаты быстрого поиска (следующая строка)
CARD_SEARCH_START dd.MM.yyyy_HH:mm:ss
$<paramId> <значение параметра ...>             # один или несколько параметров карточки
CARD_SEARCH_END
<searchId> <docId> <docId> ...                  # результаты поиска по карточке
DOC_OPEN dd.MM.yyyy_HH:mm:ss <searchId> <docId> # открытие документа (4 поля)
SESSION_END dd.MM.yyyy_HH:mm:ss
```

`searchId` связывает `DOC_OPEN` с конкретным поиском (QS или карточкой) внутри сессии.

### Неоднозначности формата и принятые решения

- **`DOC_OPEN` без timestamp.** В данных встречается легаси-форма из 3 полей
  `DOC_OPEN <searchId> <docId>` (6 566 строк) без собственной метки времени. Для группировки по
  дням таким открытиям присваивается **дата сессии** — последняя известная метка времени,
  встреченная в сессии до этого открытия.
- **Трактовка метрики 1.** Считается число **блоков** `CARD_SEARCH`, в которых хотя бы один
  параметр имеет значение `ACC_45616` (параметр `$0` — поиск по идентификатору документа).
- **`searchId` уникален в пределах сессии**, но может повторяться между сессиями, поэтому каждая
  сессия парсится независимо (см. ниже).
- **Устойчивость к битым строкам.** Любая строка, вызвавшая исключение при разборе, пропускается и
  учитывается диагностическим аккумулятором (на текущих данных таких строк нет).

## Подход и почему именно RDD

Используется **Spark RDD + `wholeTextFiles`** (а не DataFrame):

- разбор зависит от **порядка строк внутри сессии** (строка результатов идёт сразу за `QS` /
  `CARD_SEARCH_END`; нужно связать `searchId` ? тип поиска, а затем `DOC_OPEN` ? поиск). Это плохо
  ложится на табличный API, но естественно выражается пер-сессионным парсингом;
- `wholeTextFiles` держит сессию целиком в одной записи ? корректная привязка `DOC_OPEN` к поиску
  без межсессионных коллизий `searchId`.

Применяемые хорошие практики Spark:

- нет `collect()` на больших данных (для сводки используется `take`);
- нет `groupByKey` — агрегация через `reduceByKey` (map-side combine);
- распарсенный RDD кэшируется, т.к. участвует в двух действиях;
- аккумуляторы используются только для диагностики, а не для бизнес-логики (могут переоценивать при
  повторных запусках задач).

Логика разбора вынесена в чистый, не зависящий от Spark объект `LogParser` и покрыта unit-тестами
(`LogParserSpec`), что упрощает проверку корректности.

## Структура проекта

```
DE/
??? pom.xml                 # Maven, Scala 2.12 + Spark 3.5.1, shade-плагин (fat jar)
??? run.sh                  # локальный запуск (java -jar, флаги --add-opens для Java 17)
??? src/main/scala/ru/hse/consultant/
?   ??? LogParser.scala         # чистый парсер одной сессии
?   ??? SessionAnalytics.scala  # Spark-драйвер: чтение, метрики, запись
??? src/test/scala/ru/hse/consultant/
?   ??? LogParserSpec.scala      # unit-тесты парсера (ScalaTest)
??? Data/                   # входные данные (не версионируются)
??? output/                 # результаты выполнения
```

## Сборка и запуск

Требуется **JDK 17** (Spark 3.5.x не поддерживает более новые JDK) и Maven.

```bash
# сборка fat jar (с прогоном тестов)
export JAVA_HOME=$(/usr/libexec/java_home -v 17)
mvn clean package

# запуск (по умолчанию вход Data/, выход output/)
./run.sh Data output
```

`run.sh` запускает собранный jar через `java -jar` в режиме `local[*]` и добавляет необходимые на
Java 17 флаги `--add-opens`, а также привязку драйвера к `127.0.0.1`.

В IntelliJ IDEA: импортировать как Maven-проект, главный класс — `ru.hse.consultant.SessionAnalytics`,
аргументы программы — `Data output`.
